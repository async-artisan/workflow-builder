# 搭建与验证方法

## 从真实任务确定最小闭环

先了解任务为什么重复、当前最耗时或易错的动作、已有材料、期望结果、谁判断结果可用。

候选不明确时用下表比较，不机械要求用户凑固定数量：

| 候选任务 | 输入 | Agent处理 | 输出 | 人工检查 | 下次复用 | 适合先做的理由/障碍 |
| --- | --- | --- | --- | --- | --- | --- |

优先选择真实、频繁、有材料、有明确结果且容易检查的任务。对高风险、材料敏感、结果不可判断或范围过大的任务，解释具体障碍并缩小首轮输入或执行范围，由人确认最终场景。

用户选定业务目标后，区分完整流程和首次验证样本。例如全流程测试可以先覆盖一个功能，但仍保留分析、评审、执行、缺陷处理、复测和报告的阶段。范围改变须说明，不能悄悄把完整目标替换成局部文档生成。

用一张工作流卡片固定共同理解；字段可合并，但不要求为简单任务另建文件：

| 字段 | 要回答的问题 |
| --- | --- |
| 目标与对象 | 为谁解决什么重复问题，怎样算有价值 |
| 触发与频率 | 何时启动，多久发生一次，由谁启动 |
| 输入与来源 | 必需/可选材料是什么，当前是否已收到并读取 |
| 输出与验收 | 交付什么，谁依据什么标准判断可用 |
| 范围与权限 | 不做什么，允许读写哪些系统，哪些动作须另行确认 |
| 人工决策点 | 哪些方向、冲突、例外和最终接受不能由 Agent 代决 |
| 保存与复用 | 入口、SOP、结果和运行记录放在哪里，下次如何启动 |

## 工作台和执行说明

先组织任务的承载位置、职责和边界。平台缺功能时用文件夹、文档和单会话分角色，仍可形成草稿。

工作台草稿应能回答：

- 哪个项目或空间保存长期资料，本次在哪个会话/运行中执行？
- 本次目标和边界是什么？
- 谁负责总控、执行和检查，各自接收什么、输出什么？
- 需要哪些材料，哪些已交付和读取，哪些仅承诺提供？
- 哪些动作交给Agent，哪些取舍和结果必须由人判断？
- 可能沉淀什么SOP、能力和长期规则？
- 是否要读写外部系统，已有工具能否支持，未连接时怎样手动兜底？

实际执行前明确任务说明：目标、背景、输入、范围、限制、输出格式、判断标准、角色分工和缺信息时的处理方式。主动从对话与材料中整理，不要求用户先学会写提示词。

材料可使用“待提供、已收到、已读取、不可读取”的简单状态。关键问题集中问，已有答案不重问；用户暂未决定就保留待确认。推荐选项写出理由，并与已确认规则分开。不要把“已弹窗”当作完成澄清；必须等到实际答案。

开始真实运行前做就绪判断：

- 必需输入已读取，且能支撑首轮目标；可选缺口已标明影响。
- 输出位置、验收标准和授权边界明确；没有隐含的外部发布或破坏性动作。
- 每一步都有可检查产物和失败去向，工具不可用时有跳过、降级或人工处理方案。
- 若条件不足，先交付已能确定的设计和材料清单；不要用虚构输入制造“试跑成功”。

## 角色与工具

| 职责 | 主要工作 | 交接依据 |
| --- | --- | --- |
| 总控 | 判断能否开始、拆步骤、识别缺口、协调和汇总 | 任务说明、步骤、未决项与产物位置 |
| 执行 | 在输入和范围内处理，遇关键缺口提出问题 | 第一版结果、实际动作、来源和失败项 |
| 检查 | 对照要求找遗漏、事实问题、过度承诺和结构缺陷 | 问题、证据、修改建议与验证结果 |
| 人 | 确定业务方向、冲突口径、取舍与接受标准 | 可追踪的意见和决定 |

职责可由同一Agent分阶段承担。并行时明确输入输出、权限、依赖和唯一文件修改责任；分工以减少盲点和缩短等待为目的。

工具连接先回答：要消除哪个重复动作、读写什么系统、现有访问和工具是否足够、失败如何退回人工。实际需要时再配置；配置文件存在不能当成连接验证通过。

输入包含图像、音频或视频时，安排具备对应处理能力的工具/子Agent，交回可核查的文字结论和结果位置；不支持时说明具体未处理内容。工具或模型按任务能力选择，区分用户实际选定配置与建议配置，不猜测当前运行环境的底层模型或参数。

## 异常、恢复与副作用

- 为关键步骤定义失败去向：重试、换工具、降级、跳过或转人工。重试须有条件、次数或停止标准，避免无限循环和重复写入。
- 外部写入先明确目标、内容和影响；批量、发布、删除、付费等动作按授权边界单独确认。失败后先核实实际状态，避免重复提交。
- 保留已完成的有效产物和运行记录，从中断后的首个未完成步骤恢复；不要让一次局部失败抹掉全部进展。
- 密钥、令牌和私密材料不写入 SOP、模板、日志或示例；只记录所需权限和安全的配置入口。
- 对无外部工具的流程，提供手动输入/输出路径，并标出自动化尚未覆盖的部分。

## 运行、人工检查和修订

首次运行保留四个动作：

1. **判断和拆分：** 输入能否支持目标、限制是否清楚、输出能否检查；拆成少量明确步骤，每步有产物。
2. **第一版：** 按步骤真实处理。新增缺口先核实，不补造事实。部分失败和未执行项一并保留。
3. **人工反馈与修订：** 展示可检查结果，请人给具体反馈，随后修订。意见含糊时先澄清。
4. **保存：** 保留输入、步骤、第一版、反馈、修订版、保存位置、下一次可复用规则。

人工检查关注：

| 维度 | 要判断的问题 |
| --- | --- |
| 方向 | 是否解决原问题，范围、使用对象和业务规则是否正确 |
| 承诺 | 是否把未知写成事实、把建议写成决定、把未验证说成通过 |
| 结构 | 输入、步骤、字段、检查点和保存方式是否便于下次复用 |

事实和引用需回到材料核验。AI自检可先发现问题，人的业务反馈仍需真实记录。用户没有提出修改时，可以记录其明确认可及依据，不虚构差异或为了制造版本而无意义改写。

用一份业务流程说明串起状态即可，不强制为每个阶段建一套文件：

| 步骤 | 输入/前置条件 | 负责人 | 实际产物位置 | 检查结果 | 未决项与下一步 |
| --- | --- | --- | --- | --- | --- |

文件名、目录和详细输出格式按业务项目约定。保存位置不明时先给对话内草稿；不要把新的业务流程写入当前无关仓库。已经明确的保存位置直接使用。

一次运行至少保留以下可核查信息，简单任务可合并成一段记录：

```text
运行目标 / 输入及版本 / 实际执行步骤 / 产物位置
检查结果与证据 / 异常及处理 / 人工意见或待人工验收
当前状态 / 未决项 / 下一步
```

状态只按实际证据填写：“已设计”表示说明可评审；“已试跑”表示真实输入已处理；“已人工验收”表示有明确的人业务接受；“已复用验证”表示不同输入按 SOP 复跑达到冻结阈值；“已交接验证”表示独立使用者或新会话能找到入口并继续执行。各状态可部分完成，不自动向上推导。需要持久化或外部写入时，按 [运行清单与证据校验](run-manifest.md) 由工具重新推导状态，不仅靠手工勾选。

试跑、验收和交接时复制 [验收与签核模板](../assets/verification-signoff.template.md)。批准或拒绝必须引用人的明确原话并限定版本、范围和后续动作；沉默、AI 自检和 Agent 互审都不能替代人工签核。实质变更后，将旧签核标为需复核。

## 把有效经验变成长期资产

从真实运行记录中分别提炼：

| 类型 | 保存内容 | 不适合保存的内容 |
| --- | --- | --- |
| SOP | 触发、输入、执行者、任务说明和步骤、输出、人工检查、保存位置 | 一次聊天全文或只有结论没有操作 |
| 可复用能力 | 适用任务、触发方式、必要输入、输出、边界、暂存/调用位置 | 只有某一次任务有效的结果 |
| 长期规则 | 定位、偏好、禁区、长期检查标准和授权边界 | 临时任务、账号密钥、私密材料 |

能力尚未成熟时先保存候选或模板；需要参数化 SOP 或独立 Skill 时，按 [标准 SOP 与 Skill 生成](sop-format.md) 使用模板和生成器。不要因为写出候选或生成 Skill 就声称 Agent 已自动掌握、加载或验证通过。

用新的真实材料按SOP复跑，观察是否仍需临时补提示、缺字段、步骤不可执行或结果跑偏，记录卡点、反问、修改原因和修订后的规则。沿用原输入重放仅能证明该输入仍能运行。未做不同输入验证时，保留“复用未验证”，不妨碍交付设计草稿。

## 规则保存与效果验证

把个人通用偏好、项目固定流程和当次目标材料分层；规则写成可观察动作。整理时保留已有授权和平台限制，消除矛盾与空泛要求。保存位置不明或将覆盖原内容时，先说明目标与影响。

验证方法：

1. 保存一个低风险真实任务在规则设置前的结果。
2. 在合适位置保存已明确的规则，检查重复和冲突。
3. 在新运行中核对实际读取了哪些规则来源。
4. 用同一任务比较输出是否遵循新规则；没有改善就修改具体规则再测。

区分“规则文件已写入”“本次已读取”“新运行自动加载已验证”。不能启动独立新运行时，自动加载保持未验证。只支持聊天的平台可以手动附上规则和材料，并说明提供方式。

完成回报包括结果与验证、下一步，以及需要时说明用户可选的工具/模型配置和理由；无法核实的配置如实留未知，不编造运行参数。

## 审计闭环与可靠性

先还原“声称的流程”和“实际可运行的流程”，再用证据核对。每条问题包含位置、复现步骤、影响、严重度和修复建议；没有证据的疑虑标为待核实。

| 审计面 | 核心问题 |
| --- | --- |
| 输入到输出 | 必需输入是否可得，输出是否回到原业务目标并可验收 |
| 步骤与交接 | 每步是否有负责人、前置条件、产物和下一步，是否存在无主交接 |
| 异常与恢复 | 缺输入、工具失败、超时、部分完成和重复执行如何处理 |
| 权限与安全 | 是否越权读写、泄露敏感信息，或把高风险动作藏在自动步骤中 |
| 检查与承诺 | 是否区分自检、人工验收和未验证，结论能否追溯证据 |
| 复用与维护 | 新输入能否运行，规则由谁更新，变更后哪些环节需要回归 |

严重度按实际业务影响定义：阻断核心结果或无人工兜底的为阻断；可能造成错误接受、重复副作用或敏感数据问题的为高；降低效率但有明确绕行的为中/低。优先修复阻断和高严重度问题，再验证修复，不以“建议已写”代替“问题已关闭”。

根据风险选择异常测试；不要为低风险简单流程机械执行所有测试。无法安全复现外部故障时，用设计审查或受控模拟，并明确它不能证明真实系统恢复能力。

## 交接、迁移与持续维护

交付给下一位使用者时，应能找到：使用场景与对象、入口、平台/项目位置、输入材料、角色、任务说明、SOP、能力与规则、工具连接、人工检查、实际结果和复用方式。缺项标待补充，并按对使用的影响排序改进项。

迁移平台时，逐一映射项目/空间、会话/运行、Agent/角色、材料/知识、规则/记忆、Skill/模板和外部连接。没有对应功能时使用文档或单会话兜底，重新验证访问、规则加载和真实执行，不能只替换按钮名称。

流程能运行后持续收集卡点，更新SOP及规则；影响输入、输出或检查方式的改变，需要重新验证相关环节。用实际运行和复用证据评估质量，不以文件数量或格式完整代替效果。
