# 模糊需求发现与引导访谈

当用户只有模糊想法、回答零散、同时提出多个场景，或无法直接说明输入输出时使用。目标不是问完一张问卷，而是用最少的对话共同确认一个值得试做的业务结果。

## 先判断清晰度

| 情况 | 行动 |
| --- | --- |
| 目标、使用对象、输入和结果已明确 | 跳过访谈，复用已有信息进入工作流卡片 |
| 有具体场景，但缺少量关键字段 | 只问会改变首版的缺口 |
| 只有“想自动化/搭流程”等模糊想法 | 从最近一件具体重复事务开始 |
| 多个场景混在一起 | 先列候选，比较后推荐一个首版 |
| 用户中途改目标 | 更新理解回放，说明哪些旧结论失效，不沿用假设 |

不要为了显得周全而强迫清晰用户经历完整访谈。

## 从经历而不是术语开始

模糊开场优先问：

> 先不用考虑自动化。最近哪件重复做的事最让你觉得麻烦或容易出错？

得到场景后，按实际回答选择后续，不机械逐题询问：

1. **当前做法：**“你现在一般怎么做？能举一个最近发生的例子吗？”
2. **痛点：**“哪一步最耗时间，或者最容易返工？”
3. **材料：**“现在需要看哪些东西？群聊、表格、文档还是业务系统？能给一个小样本吗？”
4. **结果与对象：**“最后整理成什么样？谁会用这个结果做什么？”
5. **可接受结果：**“如果先做一个首版，你最希望它先做对哪一点？什么错误不能接受？”
6. **边界：**“先只生成草稿可以吗？有没有写回、发送、发布、删除或付费动作？”

使用用户听得懂的词。用户不知道“验收标准”时，改问“你会根据哪几点判断它能用”；不知道“输入”时，改问“你平时要找哪些材料”。

## 提问规则

- 每轮只问 1～3 个会改变结果的问题；优先一次问一个最关键问题。
- 给出生活化示例、2～4 个候选或带理由的默认建议，同时允许用户自由回答。
- 已回答的不重复问；用户跳题时先接住新信息，再决定是否仍有必要追问。
- 用户答不上来可跳过，标记未知并提供可撤销的默认首版；不得把默认建议写成用户决定。
- 不为了凑轮次或字段持续提问。信息足以形成可确认首版时就停止访谈。
- 用户明确不想回答时，交付现有理解、假设和缺口，不逼迫提供材料。

## 多场景时先收敛

用少量候选比较，不要求用户补齐固定表格：

| 候选 | 使用频率与痛点 | 现有材料 | 结果是否易判断 | 风险与首版障碍 |
| --- | --- | --- | --- | --- |
|  |  |  |  |  |

优先推荐真实、重复、有材料、结果容易检查且能低风险试做的场景。说明推荐理由和暂不做其他场景的原因，不擅自替用户决定长期优先级。

## 理解回放与样例确认

形成首版前，用 [需求发现简报](../assets/discovery-brief.template.md) 汇总，并明确分为：

- **已确认：** 用户实际说过的目标、材料和边界。
- **建议默认：** 智能体提出、用户尚未确认的首版范围或取舍。
- **仍未知：** 会阻碍设计或执行的信息；能后补的不要写成阻断项。

随后给出 [工作流卡片](../assets/workflow-card.template.md) 和一个尽量小的输出样例。样例可以使用明确标注的合成内容，只用于确认“是不是想要这种结果”，不能冒充真实试跑。

确认重点：

> 我建议首版先做 A → B，只生成草稿，不自动发送。输出大致像下面这样。这个方向和范围对吗？哪一处最不像你想要的？

用户纠正后更新卡片和样例；不要只修改文字迎合，要检查是否改变了业务目标、输入、风险或验收。

## 进入搭建的门槛

至少确认以下事项后再选择工具或生成完整 SOP：

- 业务目标和结果使用对象明确；
- 首版范围及不做什么明确；
- 结果形态或输出样例已获认可，或用户明确允许按建议试做；
- 高风险边界和人工决定点没有被隐藏。

材料、权限或工具不足不妨碍先交付设计，但真实执行仍需按运行就绪检查处理。工具选择发生在业务确认之后，而不是访谈开头。

## 避免的行为

- 一开始就询问平台、模型、MCP 或技术架构。
- 用“输入、oracle、幂等”等术语拷问非技术用户。
- 一次抛出十几个问题或要求用户先学会写提示词。
- 把候选选项当成用户选择，把“有材料”当成已收到并读取。
- 在需求仍模糊时生成看似完整的大而全流程。
- 为了推进而虚构用户反馈、样例来源或业务事实。
