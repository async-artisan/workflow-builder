# 软件测试工作流：能力组合示例

> 这是合成设计示例。下列 Skill 和 MCP 均为候选，不代表任何宿主已经安装、授权或调用成功。实际搭建时必须重新发现和验证。

## 已确认的首版业务边界

- 输入：一份已授权的需求文档、测试环境和测试账号。
- 输出：需求覆盖点、测试用例、执行证据和测试报告草稿。
- 首版只测试一个低风险功能；不自动发布、不修改生产数据。
- 缺陷先进入草稿清单；如需写入 Jira，另行确认权限和审批。

## 能力映射

| 业务步骤 | 所需能力 | 候选实现 | 交接产物 | 不可用时的首版兜底 |
| --- | --- | --- | --- | --- |
| 提取需求与约束 | 文档解析 | 现有文档解析 Skill | 带原文位置的需求点 | 人工提供文本并标注标题 |
| 生成与维护用例 | 表格读写 | 现有表格 Skill | 用例表及版本 | CSV 模板和人工编辑 |
| 执行页面测试 | 浏览器操作与断言 | 现有浏览器 Skill | 每步结果、错误和运行证据 | 人工按用例执行并记录 |
| 采集页面证据 | 截图或图像读取 | 现有截图/视觉 Skill | 截图位置与必要说明 | 人工截图并命名 |
| 汇总测试报告 | 报告生成 | 现有报告 Skill 或当前工作流模板 | 报告草稿和未决项 | 人工汇总，不虚构自动报告 |
| 创建缺陷（可选） | 外部系统写入 | 已验证的 Jira MCP/连接器或官方 API | 缺陷 ID 和写入回执 | 缺陷草稿由人创建 |

## 组合契约

1. 工作流负责业务阶段、覆盖关系、验收和异常；各 Skill 只负责约定能力。
2. 需求点必须带原文依据；用例必须关联需求点；执行结果必须关联用例。
3. 文档、表格和浏览器 Skill 的版本或内容摘要纳入 `release_id`。
4. 每个阶段使用独立产物，只有指定步骤可以修改用例表和报告。
5. 浏览器执行失败时保留已完成结果，不把未执行用例写成通过或失败。
6. 自动创建缺陷前，先完成 Jira schema 和只读验证，再确认项目、字段、重复检查、审批和回执。

## 是否需要新 Skill 或 MCP

本示例优先组合已有能力，不默认创建任何新组件。

- 如果已有报告 Skill 不适用，但报告格式在多个工作流中反复使用并有真实运行记录，可以再把稳定报告 SOP 沉淀为新 Skill。
- 如果 Jira 已有 API 或连接器可用，无需新建 MCP。
- 如果多个宿主需要共享统一的缺陷状态、回执和恢复位置，才评估独立 MCP 或共享状态服务。

## 验证重点

- 文档解析缺失是否被明确标出，而非补造需求。
- 各 Skill 的输入输出是否真正可读，而不是只看名称。
- 任一 Skill 不可用时，是否保留业务阶段和人工兜底。
- 外部写入是否有独立审批、去重和回执。
- 最终报告能否回查需求、用例、执行证据和缺陷状态。
